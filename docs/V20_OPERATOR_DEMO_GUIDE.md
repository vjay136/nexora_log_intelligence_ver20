# NLI V20 Operator and Demo Guide

This guide follows the authenticated navigation currently declared in `web/app.js` and its loader registry. It documents the shipped operator surface; design specifications elsewhere in `docs/` are not proof of an implemented control. Availability and actions are role-gated. The controller API is the source of truth; the browser is a same-origin client. Use a controller WebView or configured hosted proxy, not a static preview.

## Start here

Prerequisites: a reachable Ver20 controller, a provisioned account, browser access to its HTTPS WebView/proxy, and permissions for the actions being demonstrated. Sign in and wait for controller health. The top bar reports session, refresh, stream, and freshness state. Use Refresh after correcting connectivity. Never use production secrets or sensitive raw logs for a demo. Configuration changes, approvals, publish, rollout, reprocessing, fixture purge, and user changes are real controller actions; use an isolated demo controller for those.

**State vocabulary.** `live` means recent controller telemetry under the target; source activity can still be idle. `ready` means the subsystem reports initialized without active work. `idle` means the controller has no current work/evidence; it does not mean failure. `unavailable` means the source did not provide a measurement, not zero. `delayed`/`stale` identifies age; inspect source freshness and transport separately. A request error is rendered as an error state/notification; authorization failures do not grant access. Empty-state messages are expected when no records exist. Do not interpret a blank chart or missing metric as success.

## Significant inner tabs

### Monitoring (11 views)

`Overview` summarizes current aggregate rates and state; `Fleet & Nodes` groups node health; `Pipeline` presents ingestion/normalization stages; `Sources` lists source activity; `Parser Performance` shows available parser measurements; `Destinations` shows available destination telemetry; `Queues / Replay / Quarantine` groups queue and recovery signals; `Infrastructure` shows available host/controller signals; `Latency & Synchronization` focuses on transport, freshness and timing; `Errors & Incidents` lists bounded diagnostics; `Assurance & Release Health` links assurance/release state. Filters include range, node, source and text search. Component, destination and environment selectors are currently disabled because the canonical source contract does not provide those labels. Pause stops the view refresh; it does not stop ingestion. Resume continues viewing the shared snapshot.

### Assurance Lab (11 tools)

`Analysis` runs transient single samples and file upload analysis; `Corpus` handles multi-case validation; `Parser drafts` manages draft parser workflow; `Review queue` shows reviewable proposals; `History` shows past assurance; `Fixtures` manages retained fixtures; `Guided Parser Repair Studio (GPRS)` connects quarantine evidence and previews with the existing checksum-bound parser-candidate lifecycle; `Parser Creation Helper` assists definition drafting; `NAPI Synthesis` requests bounded candidate synthesis; `Test Plans` defines reusable scenarios; `Runs` schedules/reviews bounded runs. Supply expected JSON when claiming correctness: `{}` checks execution/evidence, not semantic accuracy. A candidate remains a draft until validation and independent approval. Fixture purge is permanent. Destination integration scenarios validate the documented local boundary and do not imply contact with production destinations.

### Quarantine-to-live recovery

From a retained quarantine row, choose **View evidence & diagnose**. The Recovery Workspace carries that record ID, evidence hash, and origin node into Assurance without treating analysis as a parser mutation. Edit and test the candidate, save its draft, submit it, then have a different reviewer approve it. Publish converts supported regex candidates into the strict sealed runtime ParserPack format and includes that exact revision and payload hash in the signed parser bundle. Fleet Sync and the normal rollout path deliver it; the originating client must report the matching applied bundle hash before the replay request is enabled or accepted. A pending rollout, controller publication, or selected target is not proof of client application. Unsupported candidate shapes remain approved/test-only and cannot be published to runtime. Evidence download, exclude/restore, and raw deletion stay individually permission-gated and audited; unretained raw input is never reconstructed.

### AI Resolution (7 categories)

`Provider` configures provider connection details on the controller; `Status` reports connection; `Results` shows remediation proposals; `Parser`, `Regex`, and `Template` show extracted proposal categories; `Approval` holds review controls. Provider use is optional. A proposal is not executed code and does not change a live parser. Approval is independent; then rerun matching deterministic evidence, create/validate a parser draft, and use normal review/rollout.

### Sync subscriber pages

`Unified Sync Fabric`, `NHLE Live`, `NAPI Live`, and `NAL Live` share `Overview`, `Live activity`, `Freshness`, and `Diagnostics`. These are tabs within each workspace, not separate data pipelines. Activity for NHLE is source rows; NAPI/NAL show bounded subsystem metadata. Freshness distinguishes controller transport from per-source age. Diagnostics show bounded issue codes, stage, component, node/source, reason and recommended action where present. Every Overview includes the full subsystem names and the measured execution order. See [Ver20 subsystem names and execution order](V20_SUBSYSTEM_ORCHESTRATION.md) for the data path and recovery path contracts.

## Real-Time Sync subsystem: operator reference

The app consumes one canonical controller snapshot (`nli.sync.v1`) with monotonic revision, generated time, one-second target interval, aggregate counters, source summaries, subsystem metadata and bounded diagnostics. Server-sent incremental updates are applied to one browser store; pages subscribe to it. The browser rejects duplicate/out-of-order or incomplete deltas and requests a full snapshot after a revision gap. An abortable shared polling recovery path runs when streaming is interrupted or proxy-buffered; reconnect and recovery are automatic. Operators can use the global Refresh for an on-demand workspace reload. There is no per-tab manual “sync now” control in these views. NURSF is the fabric name; it is not a second database or a promise that every underlying subsystem is continuously busy.

### Dashboard metric catalog and history

The dashboard exposes measurements with different lifetimes. The all-source `canonical_history` series contains received/read, parsed, quarantined, and error deltas in persisted one-minute aggregates derived from client cumulative counters; retention is up to ten years, and each query is bounded to 1000 buckets. Its freshness reports the latest accepted source-counter observation. Parse latency/rate and AI request series come from bounded in-memory event metadata, so they can be empty after restart and are not durable log history. CPU, memory, and load figures are current controller runtime values or client heartbeat samples; controller CPU percentage is unavailable in this contract, and client measurements remain unavailable when the host did not report them. Missing, stale, idle, and zero are different states. No metric history stores raw lines, parsed event bodies, or secrets.

| Component | Responsibility represented in this release | Source/state interpretation |
|---|---|---|
| Nexora Unified Real-Time Synchronization Fabric (NURSF) | Shared telemetry transport, revision ordering, snapshot/delta handling, source freshness, bounded issue diagnostics and browser apply delay. | `/sync/snapshot` plus incremental SSE. `live` describes recent controller delivery; `stale` causes automatic recovery attempts. Sequence gaps trigger resnapshot. |
| Nexora Hypersonic Log Engine (NHLE) | Ingestion subsystem telemetry: source count, nodes, records read/normalized/quarantined, queue depth, rates, per-source phase and freshness. | Published source/sync telemetry. No source is a valid empty state. Queue/backpressure and stale source must be inspected even if transport is live. |
| Nexora Adaptive Parser Intelligence (NAPI) | Parser synthesis activity counters and pending proposals/drafts. | Canonical subsystem metadata; detailed work lives in Assurance → NAPI Synthesis. Zero requests means idle, not a failure. Candidate creation is operator initiated through the workflow. |
| Nexora Assurance Lab (NAL) | Assurance run counts and latest timestamps. | Canonical subsystem metadata; individual plans/runs live in Assurance. Run creation/scheduling is manual/operator-triggered, with bounded worker progress; no runs means idle. |
| Nexora Universal Parsing Intelligence & Recovery Engine (NUPIRE) / Evidence-Gated Parser Evolution (EGPE) | Evidence-backed discovery, declarative candidate artifact and held-out evaluation lifecycle. NUPIRE candidates are persisted through its workspace API. | Operator provides evidence IDs, candidate artifact and measured evaluation. This workflow is manual/operator initiated; it is not automatically invoked by ordinary ingestion. Candidate/evaluation is not equivalent to promotion or rollout. |

A healthy-looking UI is not a substitute for source evidence. Check snapshot revision/time, transport age, per-source freshness, queue/backpressure, diagnostics and the relevant subsystem’s own counters. If stream delivery pauses, observe reconnect/poll recovery and resnapshot diagnostics; use Refresh only to reload the current workspace. If it remains stale, capture the visible error/revision/time and check controller/API Monitor and host logs. Do not fabricate metrics or reset counters to make a demo look live.

## Safe manager demonstration

Use a local isolated demo controller and disposable demo user/node. For a UI-only review, read-only views and the built-in sample log are enough. For a live-flow demo, install a test client with a dedicated temporary input file containing only the sample below; configure its output to an isolated demo file. Do not edit a production input profile or endpoint. Create no provider credentials and do not upload customer data.

Sample line (synthetic):

```text
2026-10-24T10:15:30Z INFO host=demo-node service=checkout request_id=demo-001 status=200 duration_ms=18 message="synthetic checkout accepted"
```

Walkthrough (about 8 minutes):

1. Sign in; explain role-gated controls and the transport freshness indicator. Open Command Center and Monitoring, use range/source filters, and point out any unavailable dimensions explicitly.
2. Open Unified Sync Fabric → Overview, then Freshness and Diagnostics. Read revision, target interval, transport freshness and source freshness separately. If no test client is publishing, call the source view idle and continue; do not imply live ingestion.
3. Open NHLE Live → Live activity and Streams to show the synthetic test source only if the demo client is running. Expected route/counters depend on parser/config; do not promise a particular parse outcome. Otherwise show the empty state.
4. Open Assurance → Analysis, submit the synthetic line as a transient sample with expected JSON such as `{"host":"demo-node","service":"checkout","request_id":"demo-001","status":200,"duration_ms":18}` only if those are the exact intended fields. Explain that mismatches are useful evidence. Clear transient content afterward.
5. Open **UPES · Parser Recovery**. Walk its tabs: Live Failure Observatory, Recovery Decision Trace, Parser Repair Workshop, Knowledge Base, Discovery Jobs, Parser Health & Drift, Deployment & Rollback, and Runtime Health. Explain that visible metrics are aggregate/per-client heartbeat reports and that signature details are not returned by the canonical snapshot. Use the empty/unavailable states as shown; do not imply automatic discovery or promotion.
6. Open **Quarantine Resolution Wizard**, select a retained synthetic failure, and follow Select → Inspect → Schema → Map → Generate → Test → Review → Replay → Verify. Confirm each field's source evidence and leave ambiguous delimiter values unresolved until explicitly confirmed. Creating a candidate remains a draft; submission requires an independent reviewer, publication requires the approved checksum, and replay remains blocked until the originating client reports the exact applied bundle. The Assurance Lab GPRS view remains available for detailed lifecycle evidence. Avoid performing rollout/replay during an executive walkthrough.
7. Show NAPI Synthesis/NUPIRE only with a pre-created disposable evidence set. Explain training vs held-out separation, draft status, and human review gates. Then show AI remediation as the final fallback after deterministic parsing and UPES/GPRS diagnosis. A client-local AI result is staged only; it cannot enter the active registry or become assigned to a Drain cluster until it completes the managed independent-approval, signed-rollout, and applied-hash acknowledgement path.
8. Finish at NAL Live / Assurance Runs and Parser Fleet Sync. Show how run evidence and applied hashes are checked independently. State that release/rollout actions need a separate change window and approval.

## Traceability

Navigation IDs and titles are sourced from `NAV` in `web/app.js`; the loader list and renderer identify controller data paths. Relevant endpoint contracts are under `internal/api`, `telemetry`, and the web UI. When a route is added or renamed, update this inventory and run `npm run web:check`.
